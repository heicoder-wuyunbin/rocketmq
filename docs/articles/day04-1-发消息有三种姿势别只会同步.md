# 发消息有三种姿势，别只会同步

有一次，一家电商客户跟我诉苦：大促当天，他们的下单接口突然"变慢了"。排查一圈，问题不在数据库，不在缓存，而在消息发送——工程师在每一笔订单里都用了**同步发消息**：发一条，原地死等 Broker 回个"收到了"，才往下走。

大促前，一天几千单，等得起。大促时，一秒几万单，主线程全堵在"等回执"这一件事上，接口自然就垮了。

这让我想起一句话：**不是所有消息，都值得你停下来等它回话。**

今天我们就把消息发送的"三兄弟"一次讲透。

---

## 一、底层逻辑：你在对"可靠性"和"时延"做取舍

很多教程把发送方式当成"功能列表"来介绍，这是本末倒置。

三兄弟的本质，不是 API 长得不一样，而是你在这条消息上，愿意拿**多少可靠性**，去换**多低时延**。

- 你愿意等，想立刻确认"成了没" → 选**同步**。
- 你不心疼等，但要主线程别被绑死，且能接受"事后补偿" → 选**异步**。
- 你连"成没成"都不在意，只要快、只要发出去就行 → 选**单向**。

记住这个坐标：**可靠性向下、时延也向下的是同步；可靠性高、时延低的是异步；时延最低、可靠性最差的是单向。** 看明白这条曲线，选型就不会乱。

---

## 二、第一：同步发送，稳，但慢在"等"这个动作

同步发送的逻辑最直白：你调 `producer.send(msg)`，当前线程就**阻塞**住，直到 Broker 把 `SendResult` 递回来，才继续往下执行。

```java
public SendResult syncSend(String topic, String tags, String body) throws Exception {
    return producer.send(new Message(topic, tags, body.getBytes(...)));
}
```

注意，它是有**返回值**的——返回的就是 Broker 的回执。你立刻知道这条消息到底存没存进去。

**观点**：它最可靠，代价是"等"。

**场景**：下单、扣库存、支付结果通知。这类业务，你必须确认消息落地，否则后续链路全乱。所以"等"是值得的。

**解读**：同步慢，不是慢在发送本身，而是慢在"请求—应答"这一整个往返。每发一条，主线程就被占用一个往返的时间。所以 Day2 那种写法，在低频场景完全没问题；一旦上量，瓶颈就暴露了。

---

## 三、第二：异步发送，不等，但你要会"接电话"

异步发送，是把"等"这件事从主线程里拿掉了。

你调 `producer.send(msg, callback)`，当前线程**立刻返回**去干别的，Broker 的回执到达后，RocketMQ 在它自己的**回调线程池**里，调你的 `onSuccess` 或 `onException`。

```java
producer.send(msg, new SendCallback() {
    @Override
    public void onSuccess(SendResult result) { /* 收到了 */ }
    @Override
    public void onException(Throwable e) { /* 失败了，自己补偿 */ }
});
```

吞吐量为什么一下就上去了？因为主线程不再被每条消息的往返绑住，它能一口气把十万条消息"甩"出去。

但异步有两个坑，今天必须说破，否则你迟早踩雷：

**第一，回调不在你的业务线程里。** 它跑在 RocketMQ 内部的发送回调线程池。所以回调里**千万别写重逻辑**——你若在那里查库、调接口、算大数，就拖慢了整个线程池，连累所有异步消息。回调里只做"记账"：拿到结果、存个状态、发个通知即可。

**第二，异常不会抛到你业务代码。** 网络抖动、Broker 繁忙，失败走的是 `onException`，不是 `try-catch`。你要是不在 `onException` 里写补偿（落库、重试、告警），这条消息就**悄悄没了**。异步是"把压力交出去"，不是"把责任推出去"。

测试代码里用 `CountDownLatch` 等回调触发，就是要验证：你发出去之后，结果确实通过回调通道回来了，而不是石沉大海。

---

## 四、第三：单向发送，最快，也最"不负责任"

单向发送，是三兄弟里最极端的那一个。

```java
producer.sendOneway(msg);   // 无返回值，不等也不回调
```

你看，连返回值都没有。它发完就走，不等回执，也不要回调，连"成没成"都不问。

它是三者里**最快**的，因为"等确认"这一步被彻底省掉了。但代价刻在骨子里：**消息可能丢，而且你永远不会知道。**

**观点**：它只配用在"丢了也无所谓"的场景。

**场景**：访问日志、用户行为埋点、metrics 上报。你绝不会拿它发订单、发转账、发库存扣减。因为这些消息一旦丢了，业务就错了；而单向发送，连"我丢了"都不会告诉你。

---

## 五、怎么办：一张落地清单

讲到这里，方法已经清楚。给你 4 条可照着用的选型清单：

1. **要确认结果、不能丢** → 用**同步**。下单、扣库存、支付通知这类"发了必须知道成没成"的关键链路，老老实实等。
2. **要高吞吐、主线程不能卡、且失败能补偿** → 用**异步**。回调里只做轻量记账，失败补偿写在 `onException` 里，别让消息静默消失。
3. **丢了无所谓、只要快** → 用**单向**。日志、埋点、监控数据，放心甩，但绝不动核心业务。
4. **回调里不做重活、异常自己接** → 这是异步的铁律。把"可靠性"和"时延"的决策权，收回到你自己手里，而不是交给运气。

三兄弟不是"越新越好"，是**按场景选**。选错，轻则性能崩，重则数据丢。发送看似一个动作，其实是你对这条消息的一次"性格选择"：你愿意为它等多久？又能接受它丢吗？
