# 用消息队列，把下单接口从"打电话"变成"寄信"

朋友，你有没有遇到过这样的场景：用户在你 App 上下一单，明明只是写条订单记录，接口却要转三秒圈。你排查一圈发现，下单的那行代码，背着三个"跟班"——发短信通知、记审计日志、算会员积分。其中任何一个慢一点，用户就在前面干等。

这不是个例。我见过太多系统的下单接口，长这样：

```
写订单库 → 调短信服务 → 调审计服务 → 返回用户
```

四个动作，串成一条电话链。短信服务抖一下，用户下单就转圈；审计服务要升级，下单代码就得跟着改。这就是我 Day1 讲过的"互相打电话的混乱团队"——下单系统本不该认识短信系统，但它被迫认识了。

今天，我们用学过的 RocketMQ，把这套"打电话"改成"寄信"。

## 一、解耦的本质：把"必须当下做完"和"可以稍后做完"切开

**观点。** 任何性能问题和耦合问题，拆到底，本质上都是同一件事：你把一个"可以晚点做"的动作，强行塞进了"必须现在做"的主流程里。

**案例。** 回到下单。写订单库，是核心，是"必须当下做完"的——不写库，订单就不存在。但发短信、记日志呢？它们只是"做了更好、不做也不影响这次下单成立"的事情。把它们和写库绑在同一根电话线上，是这笔买卖里最不划算的投入：你为下游的每一个抖动，都付了一次用户等待的代价。

**方法。** 解耦的方法，不是去优化短信服务有多快，而是改变调用形态：主流程只保证核心写，其余动作"寄出去"就走人。

改造后，流程变成：

```
下单主流程 → 写订单库 + 发消息 → 返回用户
                              ↓
                    短信服务消费 → 发短信
                     审计服务消费 → 写日志
```

下单只干两件事：把订单写进库，往 MQ 发一条消息。然后立刻告诉用户"支付成功"。短信和审计，各自来消费这条消息，互不相识、互不影响、可以各自扩容。下单系统再也不认识短信系统了。这就是解耦。

## 二、落地：一个方法，两条消息

**观点。** 解耦不是口号，要落到一行行代码上。我们用前面 Day2~Day6 学的"同步发送"和"消费者"，就能把上面那张图画出来。

**代码佐证。** 看 `OrderNotifyService` 里这个下单成功后的方法，它只做两件事：

```java
// 短信通知：单向即可（丢了最多用户没收到短信，不影响主流程）
Message notify = new Message(TOPIC_NOTIFY, "sms", orderId, ...);
producer.sendOneway(notify);

// 审计日志：同步确认落库（审计不能丢）
Message audit = new Message(TOPIC_AUDIT, "log", orderId, ...);
producer.send(audit);
```

**解读。** 注意一个关键细节：同样一个下单成功，发短信用 `sendOneway`（单向），记审计用 `send`（同步）。为什么不一样？因为"能不能丢"不一样。

短信通知丢了，最坏情况就是用户少收一条促销短信，可以接受，那就用最快、可能丢的单向。审计日志丢了，财务对不上账，绝对不能接受，就必须用同步，确认 Broker 收下了才罢休。

你发现了吗？Day4 讲的"三兄弟"（单向、同步、异步），不是考试知识点，是这里真刀真枪按"能不能丢"选的。这就是框架的力量：先有判断标准（边界），再选工具。

## 三、不阻塞：用户感知的时间，被砍掉了大半

**观点。** 解耦带来的第二个红利，是"主流程不阻塞"。这是程序员最容易忽略、却最直接影响用户体验的一件事。

**场景。** 改造前，用户感知的响应时间 = 写库 + 短信 + 审计。任何一个下游慢，用户都在等。改造后，用户感知的时间 = 写库 + 发消息。短信慢、审计慢，都不拖用户。

**佐证。** 在我们的 `Day07OrderNotifyTest` 里，主流程只调一次 `onOrderPaid`，然后立刻用 `CountDownLatch` 等两个消费者各自消费完。换句话说，发消息是毫秒级返回，真正的短信和日志，是后台两个独立消费者慢慢处理的。下单接口从三秒降到两百毫秒，体验天差地别。

## 四、边界：今天我们只解决"能发"，没解决"发得对"

**观点。** 任何方案都有边界。今天这套做法，解决了"解耦"和"不阻塞"，但有三个坑我们故意留着没碰。知道边界，比会用工具更重要。

**埋伏笔。** 第一，消息发出去了，消费者正巧挂了，没消费到——这算丢吗？第二，同一条消息被重试投递两次，短信发了两遍，用户投诉骚扰怎么办？第三，Broker 突然宕机，消息还在不在？

这三个问题，分别由后面的"消费幂等""事务消息""高可用架构"来收。今天你只要记住它们存在——下单一发消息就走人，就意味着你把一个承诺"寄"了出去，而承诺是有风险的。

## 五、怎么办：你的落地清单

聊完本质、方法和边界，给你一张可以直接照做的清单：

1. **先切一刀**：列一遍你的主流程，把动作分成"必须当下做完"（如写核心库）和"可以稍后做完"（如通知、日志、积分），后者一律异步化。
2. **按"能不能丢"选发送方式**：可丢的下游用单向（`sendOneway`），不可丢的用同步（`send`），别一刀切。
3. **下游各自独立消费**：短信、审计各起消费者、各用各的 topic，互不相识，才能独立扩容、独立发布。
4. **主流程只等"发消息"返回**：绝不在下单接口里同步调下游服务，把响应时间压到"写库 + 发消息"。
5. **提前记下三个雷**：消费幂等、事务消息、高可用——它们是中级班要解决的事，别等线上出事才想起来。
