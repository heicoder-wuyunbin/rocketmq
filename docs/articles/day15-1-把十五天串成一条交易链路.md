# 把十五天，串成一条交易链路

你有没有过这种时刻：学了十五天 RocketMQ，每个知识点单独考都答得上来——事务消息、顺序消息、延迟消息、消费幂等，个个耳熟能详。可真让你设计一条"用户下单"的链路，你却卡住了。

问题不在"会不会用"，而在"什么时候该用哪个"。

这恰恰是架构能力的本质：**架构能力，不是把单个技术点背得更熟，而是把一堆零件组合成"可靠系统"的判断力。** 落到交易链路，这个判断力只有四句话——顺序保流转、延迟管时效、事务保一致、幂等防重复。

下面，我把一条真实电商交易链路拆给你看。

## 一、一条下单请求，背后四条消息

同一个"支付"动作，其实藏着四个性质完全不同的需求，必须用四种不同的消息能力去满足。

**第一，扣库存——事务消息兜底一致。**
观点：订单库和库存库是两个库，不能用本地事务一把锁死。
场景：本地下单成功了，库存服务却还没扣；或者反过来，库存扣了订单却没生成。
代码佐证：用事务消息，本地事务成功，半消息才对库存服务可见；失败则回滚，库存不动。
解读：这是 Day12 的最终一致——不追求"同一瞬间都成功"，而追求"要么都成，要么都不动"。

**第二，订单状态流转——顺序消息防乱序。**
观点：订单状态 `CREATED→PAID→SHIPPED` 不能乱序，否则"已发货"可能排在"已支付"前面。
场景：并发支付下，两条状态消息若落到不同队列并行消费，顺序就崩了。
代码佐证：用 `MessageQueueSelector` 按 `orderId` 路由固定队列，串行消费。
解读：顺序的本质不是"快"，而是"确定性"——同一笔订单的消息，永远在同一条队列里排队。

**第三，未支付关单——延迟消息管时效。**
观点：30 分钟不付就关单，这是"定时触发"需求，不该用定时任务扫全表。
场景：千万级订单，扫表关单既慢又浪费。
代码佐证：RocketMQ 用 18 个固定延迟等级，30 分钟对应等级 16。

```java
msg.setDelayTimeLevel(16);              // 30 分钟关单
int level = svc.closeOrderDelayLevel(); // 返回 16
```

解读：延迟消息的本质是"把时间也变成一条消息"，到点自然投递，省掉扫表成本。注意它只有固定等级，不能随心所欲定时。

**第四，通知加积分——幂等防重。**
观点：通知用普通消息即可，但网络重发、消费重试必然重复，积分不能加两次。
场景：用户付完款，积分被加了三次。
代码佐证：

```java
if (idempotent.handle("score:" + orderId))
    return "scored";        // 首次处理
return "ignored:duplicate"; // 重复直接忽略
```

解读：幂等的本质不是"不重复"，而是"重复了也不出错"——把"至少一次投递"变成"恰好一次效果"。

你看，一条链路把事务、顺序、延迟、幂等全用上了。单独看每个都不难，难的是知道"什么时候该用哪个"。

## 二、架构判断的框架：本质 / 方法 / 边界

把上面的实战抽象成可复用的判断力，就三层：

**第一，本质**：顺序保流转、延迟管时效、事务保一致、幂等防重复。这四句话，是交易链路的底层逻辑。

**第二，方法**：不要为用技术而用技术。接到一个消息需求，先问"这条消息怕什么"——怕乱序用顺序、怕丢失用事务、怕超时用延迟、怕重复用幂等。怕什么，就上什么。

**第三，边界**：四种能力都不是万能药。顺序消息牺牲并行度；事务消息有回查成本；延迟消息只有 18 个固定等级，覆盖不了任意时间。知道边界，才知道什么时候该换方案（比如任意时刻调度请交给外部定时任务）。

## 三、生产避坑清单

我把它压成七条，建议贴在工位上：

1. **Topic 按业务划，队列数按并行度定**——别用 Tag 当分类。Tag 是过滤不是路由，当成分类会埋坑（Day5）。
2. **消息别太大**，单条建议 ≤ 512KB。大 JSON 拆文件或落库传 ID，别把 Broker 当数据库。
3. **消费必须幂等**：重试必然重复，去重表 / SETNX / 状态机三选一。这是生产事故第一来源（Day11）。
4. **发送方式按"能不能丢"选**：关键同步、日志单向、高吞吐异步（Day4）。
5. **监控堆积 Diff**：早告警比堆成山再救强百倍，盯 Dashboard 的 Diff / TPS / 延迟（Day13）。
6. **生产 / 消费组命名见名知意**，排查时省的是命。
7. **重要业务上 DLedger 多副本**，主挂自动切，别赌单机不宕（Day14）。

## 四、面试高频题串讲

如果面试官问 RocketMQ，这五问覆盖八成考点，背后就是上面的"四句话"：

- **怎么保证不丢？** 同步双写 + `SYNC_FLUSH` + 事务消息兜底。→ "事务保一致"的延伸。
- **怎么保证不重复？** 消费端幂等。→ "幂等防重复"。
- **怎么保证顺序？** 分区顺序 + `MessageQueueSelector`。→ "顺序保流转"。
- **积压了怎么办？** 扩容实例（≤ 队列数）+ 消费端限流。→ 边界意识。
- **高可用怎么做的？** NameServer 无状态 + DLedger 自动切换。→ "守得住"。

一句总纲：**发得对、收得稳、排得顺、守得住。**

## 五、怎么办：上线前自检清单

学了判断框架，落地要有清单。上线一条交易链路前，对着这五条过一遍：

1. **链路图先画**：能否一句话说清"哪条消息怕什么"？说不清，就还没设计完。
2. **幂等必查**：每个消费者都问一句"这条消息重复来了怎么办"，没答案不许上线。
3. **顺序必验**：凡涉及状态流转，确认 key 路由到固定队列，并压测验证不乱序。
4. **延迟必核**：确认 18 个固定延迟等级够用，覆盖不了的需求，提前找外部调度补位。
5. **监控必接**：堆积 Diff 告警阈值设好，没告警的链路等于裸奔。
