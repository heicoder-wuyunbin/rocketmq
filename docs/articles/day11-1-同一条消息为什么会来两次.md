# 同一条消息，为什么会来两次

用户只付了一次款，账单却扣了两次。客服电话被打爆，财务对不上账，你被拉进紧急会议。

你查了日志：消息只发了一次。但消费端确实执行了两遍扣款。

问题出在哪？别急着甩锅给中间件。**这恰恰是消息队列"正常工作"的样子。**

---

## 一、底层逻辑：MQ 保证"至少一次"，不保证"恰好一次"

先认清一个事实。

RocketMQ 向消费者承诺的投递语义，叫 **at-least-once（至少一次）**，而不是 exactly-once（恰好一次）。

这二者的差别，是商业世界的基本常识：把"不丢消息"的优先级，放在"不重消息"之上。

为什么？因为丢一条消息，可能意味着一笔订单凭空消失、一笔转账永远不到账——不可接受的损失。而多来一条消息，代价可被"事后弥补"。设计者选择了"宁可多给一次，绝不漏给一次"。

所以，**重复投递不是 bug，是设计事实；而"消费不重复生效"，是你的责任。**

为什么会来两次？因为只要消费过程里出现一次失败、超时或网络抖动，Broker 就会把它再投一遍——你躲不掉。

---

## 二、第一板斧的逻辑：重试，是给故障一次自愈的机会

消费时返回 `RECONSUME_LATER`，Broker 就会重新投递这条消息。默认**最多重试 16 次**，间隔退避：

> 10 秒 → 30 秒 → 1 分钟 → 2 分钟 …… 一直拉到 2 小时。

这些重试消息，不会回到原 Topic，而是进一个内部 Topic：**`%RETRY%你的消费组`**。Broker 按退避节奏，一拍一拍地再投给你。

为什么要"退避"？因为很多失败是 **transient（瞬时）故障**：数据库抖一下、接口超时一秒、代码踩到空指针。给点时间，它自愈了，第 3 次重试就能成功。

退避的本质，是不在系统最虚弱时反复鞭尸——否则重试风暴反而把脆弱的系统打垮。

代码佐证，命名规则就藏在这两行里：

```java
public static String retryTopic(String group) {
    return "%RETRY%" + group;     // 重试消息的归宿
}
```

---

## 三、第二板斧的逻辑：死信，是 MQ 对你说"这条我搞不定了"

如果 16 次退避重试全部失败（比如消费逻辑有 bug，每次必抛异常），Broker 就不再重试，把消息丢进 **`%DLQ%你的消费组`** 这个死信队列。

```java
public static String deadLetterTopic(String group) {
    return "%DLQ%" + group;       // 死信消息的归宿
}
```

死信队列，**不再自动重试**。它等于 Broker 摊开手对你说："我尽最大努力了，这条真的搞不定，交给你。"

所以请记住一句话：**死信不是"消息丢了"，是"交给人工"。**

运维必须监控死信队列，不能放任堆积。那里躺着的每一条消息，都代表一笔没能处理完的真实业务。放任不管，就是一笔笔坏账。

---

## 四、第三板斧的逻辑：幂等，是你的责任

前面铺垫到此，结论已经呼之欲出。

重试会来、网络会重发、死信会有人工重投——**同一条业务消息，一定会来两次、三次、甚至更多次**。

如果你的消费逻辑是"账户扣款 100 元"，且没做防护，那它每来一次就扣一次。用户付一次款，账单扣三次。这就是开篇那场紧急会议的由来。

**幂等（Idempotent）**：同一条消息，处理一次和处理多次，业务效果完全相同。

怎么落地？三板斧，从最稳到最快：

**第一，唯一键去重表。** 消费前先往数据库插一条 `(订单号 + 扣款类型)`，靠唯一约束挡住重复插入。插得进=首次；插不进=重复，直接返回。最稳，因为去重交给了数据库强一致性。

**第二，Redis SETNX。** `SETNX order:1001:deduct 1`，键存在即跳过。简单粗暴、性能极高，适合不需持久审计的场景。

**第三，业务状态机。** 订单状态已是 `PAID`，直接返回，绝不重复扣款。本质是用业务状态天然去重——连"去重表"都不用额外建。

三板斧不互斥，生产里常见组合拳：**状态机兜底 + 唯一键防并发**。

## 五、实战：扣款消息，来三次也只扣一次

看一段实战逻辑。扣款消费的第一步，永远是用业务主键（`订单号 + 扣款类型`）去问一句："这条我处理过吗？"

- 处理过 → 直接返回，什么都不做；
- 没处理过 → 才执行真正的扣款，并落一条处理记录。

我们用一个最小模型演示这个"首次 / 重复"的判断。核心就一行：

```java
private final Set<String> processed = ConcurrentHashMap.newKeySet();

public boolean handle(String bizKey) {
    return processed.add(bizKey);  // 加得进=true(首次)；加不进=false(重复)
}
```

`handle` 返回 `true` 表示这是第一次，放心执行扣款；返回 `false` 表示重复，直接跳过。注意：真实生产里这个 `Set` 要换成数据库唯一键或 Redis，否则进程一重启去重就失效了。

测试怎么证伪？把同一条扣款消息模拟投递 3 次：

```java
assertTrue(svc.handle("deduct:ORDER-3001:100"));   // 第 1 次：处理
assertFalse(svc.handle("deduct:ORDER-3001:100"));  // 第 2 次：去重
assertFalse(svc.handle("deduct:ORDER-3001:100"));  // 第 3 次：去重
assertEquals(1, svc.processedCount());             // 只真正处理 1 次
```

三次投递，只扣一次——这就是幂等的力量。

## 六、怎么办：给你一张落地清单

中级班收官，给你 5 条马上能用的行动项：

1. **默认接受重复**：写任何消费逻辑前，先在心里假设"这条消息会来三次"，再动手。
2. **重试要设上限与退避**：用 RocketMQ 默认的 16 次退避，别一失败就死循环猛冲。
3. **死信必须有人盯**：把 `%DLQ%消费组` 接进告警，定期有人工核销流程，别让它变成"黑洞"。
4. **消费必须幂等**：扣款、发券、改状态这类写操作，三板斧至少上一道。
5. **加测试守住底线**：像 `Day11RetryIdempotentTest` 那样，同 key 投三次断言只处理一次，写进 CI 红线。
