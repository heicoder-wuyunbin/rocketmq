# 消息堆成山了，先别慌

凌晨两点，你的手机被告警炸醒：「RocketMQ 积压 500 万条，Diff 还在涨」。大促流量洪峰像潮水一样涌进来，订单消息铺天盖地，消费端却像拿吸管喝洪水——怎么也追不上。运维在群里 @ 你，老板在群里 @ 你，你盯着那根笔直向上的曲线，手心冒汗。

这时候，慌，是没用的。你越慌，越容易拍脑袋——「加机器！」结果哐哐加了 200 台，积压纹丝不动。为什么？因为你还没看清楚，这到底是一道什么题。

## 一、本质：积压是一道不等式

所有的消息积压，剥开层层表象，本质都是同一道题：

> 生产速率 ＞ 消费速率，且这种失衡是「暂时」的。

请注意「暂时」这两个字。如果生产永远大于消费，那不叫积压，叫架构设计失败——你该回去重写系统，而不是来救火。我们讨论的，是洪峰来时短暂失衡、洪峰过去能追平的正常波动。

所以治理的逻辑只有两条路：**要么把消费能力提上去（提速率），要么把生产峰削下来（限流、跳非关键）**。世上所有花哨的治理手段，都逃不出这两句。这，就是底层逻辑。

那为什么消费会跟不上？把病根拆开，无非三种。

**第一，消费慢。** 这是「处理能力」的病。你的消费逻辑太重——一条消息进来，先查库、再调三个外部接口、最后落盘，单条耗时 300 毫秒。生产方一秒发 2000 条，你一秒只能处理 30 条，能不堆吗？

**第二，消费挂。** 这是「可用性」的病。消费实例全挂了，队列没人拉，消息只进不出，画出来是一条笔直向上的直线。

**第三，突发流量。** 这是「容量规划」的病。大促瞬时洪峰，生产者猛发，消费端没提前扩容，于是被峰值按在地上摩擦。

定位的第一步，永远是看堆积量。Dashboard 里有个字段叫 `Diff`，它等于「Broker 消息总量 − 已消费进度」。它在涨，说明失衡还在恶化；它在降，说明你在追平。这一个数字，就能告诉你该不该从床上爬起来救火。

## 二、应急三板斧：先止血，再治病

确认了是「暂时失衡」，不是架构失败，就上应急手段。顺序很重要——先止血，再治病。

**第一板斧，扩容消费实例。** 同消费组的机器加一台，队列就自动被分摊（这是 Day6 集群模式的原理）。但这里有个硬边界：**实例数超过队列数，多出来的全是摆设**。比如你只有 4 个队列，加 8 台机器，也只有 4 台能分到活干，其余 4 台干瞪眼。这不是 RocketMQ 的缺陷，是数学的限制——这是 Day3 讲过的并行度。

**第二板斧，提升消费线程数。** 单实例内部，把 `setConsumeThreadMax` 调大，让一台机器并发更高。同样，别超过队列数——线程再多，没有队列可拉也是空转。

```java
// 单实例线程数建议：min(队列数, 20)，多了只是空转
int threads = BacklogHandlerService.recommendConsumeThreads(queueCount);
```

**第三板斧，跳过非关键消息。** 积压太狠、业务又允许时，临时跳过非核心消息（比如营销推送、行为埋点），先把核心订单流清出来，事后批量补。这不是偷懒，是「保核心」的取舍——一直堵着，核心也跟着死。

## 三、别把下游打挂：限流是追平的前提

这里有个经典陷阱，我见过太多团队栽进去：你为了追积压，把消费并发拉到满，结果下游数据库被你打挂了。下游一挂，消费更慢，你再加并发，下游再挂——死循环，越救越乱。

所以消费端必须限流。核心思路是「线程池 + 信号量」，用 `Semaphore` 卡住同时访问下游的并发数：

```java
Semaphore permits = new Semaphore(20); // 最多 20 并发查库
// 消费前 permits.acquire()，处理完 permits.release()
```

20 个并发，超出就排队等。限流不是「慢」，是「稳」。追平积压的前提，是下游还活着。再配上 Day11 的幂等设计，跳过、重试、重复投递都不怕——处理两遍，结果一样。

## 四、别拍脑袋：用公式算该加多少

「该加多少实例？」最忌拍脑袋。给你一个量化公式，`BacklogHandlerService` 已经封装好了，代码即是答案：

```java
public static int recommendConsumerInstances(long backlog, long tpsPerConsumer) {
    if (tpsPerConsumer <= 0) return 1;
    return (int) Math.ceil((double) backlog / tpsPerConsumer);
}
```

公式很简单：

```
推荐实例数   = 向上取整(积压量 / 单实例吞吐)
预计清空秒数 = 向上取整(积压量 / (实例数 × 单实例吞吐))
单实例线程数 = min(队列数, 20)
```

回到开头的 500 万：假设单实例 2000 TPS，那需要 `ceil(5_000_000 / 2000) = 2500` 个实例才能秒级清空。这个数听着吓人，但它说的是真话——要么加机器，要么削积压，世上没有魔法。在我们的测试里，100 万积压 / 单实例 2000 TPS，算出 500 实例、秒级清空；而 4 个队列时线程建议被压在 4，正是「不超过队列数」的边界在起作用。

## 五、最好的治理，是不让它发生

监控先行，比堆成 500 万再救强一百倍。盯紧三个指标：

- **堆积量 Diff**：还有多少没消费，最直观的告警线。
- **消费 TPS**：当前消费速度，判断你是在追平还是被甩开。
- **消费延迟**：消息从发到收的平均时长，用户体验的晴雨表。

Diff 一涨就告警，而不是等告警炸了手机，才从床上爬起来。

## 怎么办：落地清单

1. **先定性**：打开 Dashboard 看 `Diff`，涨就恶化、降就追平，别急着动手。
2. **查病根**：慢（逻辑重）、挂（不可用）、突发（没扩容），对号入座再开方。
3. **上手段**：扩容实例（≤队列数）、提线程（≤队列数）、必要时跳非关键。
4. **加护栏**：消费端用信号量限流保护下游，配幂等防重复处理。
5. **定告警**：Diff / TPS / 延迟三指标上监控，洪峰来临前先扩容量。

积压不是灾难，是系统在提醒你：速率失衡了。成因三分、应急三板斧、下游限流、量化决策——按顺序走，再大的山，也能搬动。
