# 本地事务和发消息，怎么"一起成功"？

你有没有遇到过这样的线上事故：

用户下单，订单库写成功了，库存消息却没发出去。结果库存没扣，用户买到了"超卖"的货——仓库里根本没有这件商品，客服只能去道歉、赔券。

反过来呢？消息先发出去了，库存被下游扣掉，结果订单库写入失败回滚。用户没下成单，库存却凭空少了一件，财务对账对到崩溃。

这两个故事的共同特征是：**两个写操作，一个写本地数据库，一个往 MQ 发消息，结果怎么也对齐。** 今天我们就用 RocketMQ 的事务消息，把这个死结解开。

## 一、先说本质：两个写操作，没有共同的事务边界

为什么"写库"和"发消息"很难一起成功？因为它们俩，**没有共同的事务边界**。

你写一个订单，用的是本地数据库事务——`begin`、写、提交，要么全成要么全败。可发一条 MQ 消息，是往 Broker 的网络里扔一个请求，根本不在你本地事务的管辖范围内。这是两个独立的写操作，没法塞进同一个事务里原子提交。

于是就出现了开头那一幕：一个成了，另一个没成。你用再多的 `try-catch`、再多的补偿脚本，都只是在"事后擦屁股"，因为根因从一开始就在——**本地事务管不了"发一条消息"**。

那怎么办？RocketMQ 的思路很聪明，它不追求"同时成功"这个苛刻目标，而是把"发消息"这个动作，**改造成一个"可被校验的、与本地事务对齐的动作"**。

怎么改造？三件套：Half Message（半消息）、Commit/Rollback、回查。下面逐一拆开。

## 二、第一，Half Message：先把消息"藏起来"

生产者不先发正式消息，而是先发一条"半消息"给 Broker。它的关键属性是：**对消费者不可见**。下游的库存服务此刻根本看不到它。

它存在的意义，是占个位子。等本地事务（写订单库）执行完，再回头告诉 Broker：要么 Commit（半消息转正、消费者可见），要么 Rollback（直接删掉）。

看关键片段：

```java
producer.sendMessageInTransaction(msg, arg);
```

这一行背后干了两件事：先落 Half 消息，再触发本地事务。本地事务在 `executeLocalTransaction` 里执行。

逻辑链条变成：

1. 发半消息（消费者看不见）
2. 写订单库
3. 成了 → Commit，库存服务看到，去扣库存
4. 失败了 → Rollback，库存服务永远看不到

"消息最终对下游可见"和"本地事务结果"被绑死了：**本地成，消息才可见。** 一致性第一次被保住。

## 三、第二，TransactionListener：把"本地事务"和"最终决定"交给你

核心接口是 `TransactionListener`，只有两个方法却各司其职：

```java
public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
    // 写订单库（本地事务）
    return localSuccess ? COMMIT_MESSAGE : ROLLBACK_MESSAGE;
}
public LocalTransactionState checkLocalTransaction(MessageExt msg) {
    // 查本地事务日志，决定最终状态
    return decidedByLocalLog(localLogExists(msg));
}
```

`executeLocalTransaction` 是你的本地事务现场：写订单、落库、返回成或败。"订单库写入"才是真正的业务动作，消息可见性只是它的附属结论。

设计细节：本地事务**在半消息占好位之后才执行**。顺序一旦错，机制就废。这也解释了为何必须用 `sendMessageInTransaction` 专用入口——它把两个动作用框架顺序锁死，不容自由发挥。

## 四、第三，回查：生产者当场去世也不怕

前两步有漏洞：本地事务写完了，正要发 Commit，进程崩了。半消息悬在 Broker 上，没人确认，也没人否认。

Broker 不会一直悬着，它会**定时回查**你：`checkLocalTransaction` 被回调，问"这条本地事务到底成没成？"你查订单库记录，返回 Commit 或 Rollback。

代码里这个映射是回查的核心：

```java
public static LocalTransactionState decideByLocalLog(boolean localSuccess) {
    return localSuccess ? COMMIT_MESSAGE : ROLLBACK_MESSAGE;
}
```

**回查是事务消息的兜底。** 它把"确认"从"靠人记得补"做成"机制自动补"。哪怕生产者崩溃，一致性也能补齐。这就是它比"自己写补偿脚本"靠谱的原因——补偿脚本是人写的，人会忘、会漏；回查是框架兜的，准时不缺席。

## 五、第四，下单 + 扣库存：最终一致长什么样

串起来看最终一致：

- 半消息先发，订单库写成功 → Commit → 库存服务消费到 → 扣库存
- 订单库写失败 → Rollback → 库存服务收不到 → 不扣
- Commit 前崩溃 → 回查按订单库记录补决定

最终效果：**订单和库存，要么都动，要么都不动。**

必须划一条边界：事务消息保证"下单"和"发消息"一致，不保证"库存服务一定扣成功"。扣库存是下游自己的事，靠 Day11 的幂等防重复、靠重试保证落地。事务消息解决的是"边界对齐"，不是"下游一定对"。分清楚两层职责，才不会再该用幂等的地方指望事务消息。

## 六、怎么办：5 条落地清单

最后，给你一份可直接照做的清单：

1. **不要自己先写库再手发消息**，这是不一致的根源。统一走 `sendMessageInTransaction` 专用入口，让框架排好"半消息→本地事务→确认"的顺序。
2. **本地事务一定要落可查的记录**（订单状态表或事务日志）。否则回查时你无据可查，一致性的兜底就空了。
3. **`checkLocalTransaction` 必须幂等且只读本地状态**。它可能被 Broker 多次调用，绝不能产生副作用。
4. **下游消费必须做幂等**。事务消息只对齐发送边界，重复投递要靠 Day11 的防重方案兜底，否则回查补齐的一致性会被下游重复消费打破。
5. **回查要有明确的默认策略**。建议"未知状态按本地日志判定"，绝不长期返回 UNKNOWN，让半消息悬挂占用资源。

事务消息的本质，是把"两个没有共同边界的写操作"，用一个 Half + 回查的协议，重新对齐成"可被校验的、对齐的动作"。理解了这一点，分布式事务就不再是玄学，而是一套可以落地的工程方法。
