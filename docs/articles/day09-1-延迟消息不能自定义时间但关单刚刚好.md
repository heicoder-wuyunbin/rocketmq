# 延迟消息：不能自定义时间，但关单刚刚好

用户下单 30 分钟没付款，你得自动关单、把库存释放回去。这是电商最经典的一个需求。

很多团队的第一反应，是写个定时任务，每分钟扫一遍全表，把"创建超过 30 分钟且未支付"的订单捞出来处理。听起来很合理，但你想想它的代价：订单表可能上亿行，为了找那几条超时的，你得让数据库每分钟陪你全表扫描一次。这就好比为了收一封挂号信，雇人每天翻遍整个邮局的信箱——动作很重，浪费极大。

那有没有更轻的办法？有。RocketMQ 的延迟消息，就是为这种"未来的某件事"量身定做的。但它的脾气，你必须先摸清楚，否则上线第一天就会踩坑。

## 一、本质：把"未来某刻要做的动作"交给 Broker 托管

先说底层逻辑。延迟消息的本质，不是"让线程睡一会儿再干活"，而是**把"未来某刻要做的动作"提前交给消息中间件（Broker）托管**。

消息一发出去，其实已经到了 Broker 手里，只是 Broker 替你按下"暂停键"——到点之前，消费者根本看不到它。这就像你把一封信交给邮局，明确要求"30 分钟后才投递"。信早就到了邮局，只是压在柜台的某个抽屉里，时间没到，谁也取不走。

所以延迟消息几乎不占消费资源：它不进业务队列，不唤醒消费者，到点才"解冻"、才入队被消费。你不需要扫表，不需要轮询，Broker 替你守着这个时钟。

## 二、方法：18 个固定等级，不是任意时间

但 Broker 守时钟的方式，有一个关键约束：**它只认 18 个固定的延迟等级，不认你传的毫秒数**。

```
1:1s   2:5s    3:10s   4:30s   5:1m   6:2m   7:3m   8:4m   9:5m   10:6m
11:7m  12:8m   13:9m   14:10m  15:20m 16:30m 17:1h  18:2h
```

发送时，你调的是 `setDelayTimeLevel`，传一个**等级编号**，而不是"延 1800000 毫秒"：

```java
Message msg = new Message(TOPIC, "close", orderId, body);
msg.setDelayTimeLevel(16);   // 注意：传的是等级 16，代表 30 分钟
producer.send(msg);
```

这背后是个刻意的工程取舍。RocketMQ 在 Broker 内部用"时间轮（HashedWheelTimer）"机制管理延迟，把每一档延迟对应一个独立队列，到点统一推进。固定的 18 档让时间轮的刻度可枚举、调度可预测、恢复可重放——这是个用"时间轮换的精确"换"任意精度的自由"的权衡。代价是：你想延 23 分钟，对不起，表里没有。

## 三、边界：那个你一定会踩的坑

这是新手必踩的雷区：**延迟消息不能自定义任意时间，只能从 18 个等级里取最近的**。

比如业务要"23 分钟后处理"，RocketMQ 表里只有 20 分钟（level 15）和 30 分钟（level 16）。你没得选，只能向上或向下妥协。我们代码里专门写了个 `levelForMinutes` 做"向上取整"的映射：

```java
if (minutes <= 1)  return 5;    // 1 分钟
if (minutes <= 30) return 16;   // 30 分钟 → 等级 16
if (minutes <= 60) return 17;   // 1 小时
```

注意这里的设计哲学：**永远向上取最近的等级**。超时被早关单，比迟迟不关单要安全——关早了最多让用户稍等重下，关晚了库存就一直被占着。边界处理，本质是风险偏好的选择。

所以设计任何延迟业务前，先对着等级表核一遍：你的需求，表里有没有对应的档？有，爽；没有，要么妥协精度，要么换方案。

## 四、替代：需要任意精度时怎么办

如果业务真要"任意时刻"的延迟——比如用户自定义的提醒时间、精确到分钟的履约——RocketMQ 延迟消息就不够用了，得换：

- **定时任务扫表**：每分钟扫"该执行的记录"。简单粗暴，量级小完全够用，是中小系统的首选。
- **时间轮 / Redis ZSet**：自己维护一个秒级延迟队列，精度高，但你要自己管可靠性和重放。
- **调度框架**：Quartz、XXL-JOB，到点触发，适合复杂调度。

一句话原则：**等级表够用就用延迟消息，不够就换工具。** 别拿延迟消息去硬扛它不擅长的事。

## 五、实战：30 分钟关单，刚好严丝合缝

幸运的是，订单 30 分钟未支付自动关单，刚好命中 level 16。这就是延迟消息最舒服的用法——需求和档位严丝合缝。

下单时，发一条 `delayLevel=16` 的关单消息；30 分钟内用户付了款，业务状态机挡掉这条关单（已支付就不关）；没支付，关单消息到点自动入队被消费，执行关单、释放库存。整个链路无需扫表、无需轮询。

我们的测试也只断言一件事，却是最关键的一件：`levelForMinutes(30) == 16`，延迟等级必须落在 1~18。

## 结语：怎么办

延迟消息简单、好用，但本质是"固定档位的定时"。落地时记住这几条：

1. **先核等级表**：动手前对照 18 档，确认你的延迟时长在表里，或能接受最近的档。
2. **永远向上取整**：映射等级时取"不小于需求"的最近档，宁早勿晚。
3. **关单用状态机兜底**：延迟消息到点后，消费端必须再校验"订单确实未支付"，防止用户已付款被误关。
4. **精度不够就换**：任意分钟/任意时刻的需求，果断用定时任务、时间轮或调度框架，别硬扛。
5. **写测试守住边界**：像 `levelForMinutes` 一样，把"等级在 1~18"做成断言，挡住未来的手滑。

延迟消息不能自定义时间，是它的局限；但 30 分钟关单，它刚刚好。工具没有好坏，只有合不合适。
