# 一次发一百条，和按属性筛人

## 一、两个让人半夜被叫醒的冲突

**场景一：大促给 10 万用户推降价通知。** 循环里 `send` 一条条发，结果是 10 万次"请求—应答"的网络往返，把 Broker 打爆，发送线程全堵在 RTT 上。你本想高效通知，却先把管道自己堵死。

**场景二：运营说"VIP 才发券"。** 你用 Tag 做了 `vip` 标签，但下一句往往是"把 age>18 且 vip=true 的筛出来"。Tag 做不了数值比较，更做不了 `AND` 多条件。于是你让全员都收到，再在消费端自己 `if` 掉——等于把 10 万条无关消息白搬一遍。

这两个冲突本质同一件事：**别浪费**——别浪费网络往返，别浪费投递流量。今天两件套为此而生：批量发送与 SQL92 属性过滤。

---

## 二、底层逻辑：拼车，与精准投递

抽象一下，两件事都是"把成本挪到更省的地方"。

- **批量发送 = 网络层面的"拼车"。** 原本 100 人各开一辆车去同一目的地，现在拼一辆大巴一次拉完。省下的不是路程，是"发车—到站的调度开销"。
- **SQL92 过滤 = 把筛选"下推"到 Broker 的"精准投递"。** 原本你把所有消息塞给下游，让下游自己挑；现在把筛选条件写进订阅，Broker 投递前就替你筛好，只送命中的那几条。

下面所有规则，都是这两条的延伸。

---

## 三、批量发送：本质是把 100 次往返拼成 1 次

**观点：** 批量的价值不在"快"，而在"省往返"。

**场景：** 同步 100 条状态变更。逐条发是 100 次 RTT；批量发是装进一个 `List` 一次 `send` 出去。

**代码佐证（关键片段）：**
```java
for (int i = 0; i < bodies.size(); i++) {
    list.add(new Message(topic, "batch", "k" + i, ...));
}
producer.send(list);   // 一次网络往返发 N 条
```
`BatchSendService.sendBatch` 就做了这件事：攒一批，发一趟。

**解读——三条边界，记死：**
1. **单批总大小 ≤ 1MB。** 硬上限，超了拆成多批发。不是"建议"，是协议限制。
2. **必须同 Topic。** 批量不能把订单和短信混在一批发，Broker 按 Topic 路由，跨 Topic 拼不了车。
3. **不能有延迟 / 事务属性。** 批量消息不支持延迟等级和事务消息，需要就退回单条发。

这三点不满足直接报错。它们不是 Bug，是"拼车"的代价：同路才能同车。

---

## 四、Tag 不够用时，SQL92 把筛选下推到 Broker

**观点：** 当筛选条件从"是哪一类"升级成"满足什么数值关系"，Tag 就力不从心，得让 Broker 替你算。

**场景：** "vip=true 且 age>18"发券。Tag 做不了数值比较和多条件 `AND`，但 SQL92 可以——写进订阅表达式，Broker 投递前计算，只把命中的推给这个消费组。

**代码佐证（关键片段）：**
```java
// 发消息时挂属性
msg.putUserProperty("vip", "true");
msg.putUserProperty("age", "20");
// 订阅时写筛选
consumer.subscribe(topic, MessageSelector.bySql("vip = 'true' AND age > 18"));
```
`PropertyFilterService` 的 `sendWithProperty` + `consumeBySql` 即此模式：属性挂消息，筛选写订阅。

**解读：**
- **一个必踩的坑：** SQL92 过滤需 Broker 开 `enablePropertyFilter=true`。Tag 不需要，但 SQL 要。没开，表达式会"静默失效"——不报错，但全员照收。上线前先确认配置。
- **能力边界：** 支持 `= <> > >= < <= BETWEEN IN IS NULL AND OR NOT` 等，覆盖绝大多数"按属性筛人"诉求，但别当数据库用。

本质：**筛选发生在谁身上，成本就由谁承担。** 下推到 Broker，是用一点计算力换下游成百上千倍的流量节省。

---

## 五、消息发出去怎么查：keys 是你的"业务主键"

**观点：** 消息不是发出就消失，前提是你能定位它。

**场景：** 线上反馈"某用户没收到券"，要从海量消息里捞出那一条。两条路径：
- **Dashboard（rocketmq-dashboard）：** 按 Topic + keys 或 msgId 搜，看消息轨迹——谁发的、存哪、谁消费了。
- **mqadmin 命令行：** `queryMsgByKey`、`queryMsgById`。

**解读：** 这里的 `keys` 是 Day5 强调的"每条消息都设的业务主键"（如订单号），是事后定位消息的唯一抓手。**没设 keys，查时只能干瞪眼**——连"哪条"都指不出，更别谈排查。

---

## 六、实战串起来：批量同步状态 + 按属性推不同下游

**观点：** 批量解决"发得快"，SQL 过滤解决"发给谁"，两者叠加才是完整方案。

**场景：** 一次同步 100 条状态变更（同 Topic，批量发）；VIP（`vip=true`）由"营销消费组"用 SQL92 筛出，自动发券；普通用户走默认消费。批量把 100 条拼车送进 Broker，SQL 再把 VIP 精准挑给营销系统——既不打爆管道，也不让下游白搬流量。

测试 `Day10BatchFilterTest` 即微型验证：批量发 3 条普通 + 1 条 `vip=true`，SQL92 消费者只收到那条 VIP，证明"拼车"和"精准投递"同时成立。

---

## 七、怎么办：4条落地清单

1. **大批量发送先拼车：** "同 Topic、同批、无延迟事务"的消息，一律 `send(List<Message>)`，别循环单发；单批逼近 1MB 主动拆分。
2. **筛选能下推就下推：** 带数值比较的订阅，用 `MessageSelector.bySql`，把 `if` 从消费端挪到 Broker。
3. **上线前先开开关：** 用 SQL92 前确认 Broker `enablePropertyFilter=true`，否则静默失效。
4. **每条消息都设 keys：** 用业务主键（订单号、用户 ID）当 `keys`，没有它，消息查无可查。

---

批量是"发得省"，SQL 过滤是"收得准"。两者都建立在前面 Tag、属性、keys 的地基之上。地基打牢，上层才省得安心。
