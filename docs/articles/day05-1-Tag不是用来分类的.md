# Tag 不是用来分类的

你有没有见过这样一个 RocketMQ 集群：Topic 只有孤零零三五个，但每个 Topic 下面挂了几十个 Tag——订单、物流、积分、短信、审计，全塞在一起。

owner 拍着胸脯说："Tag 能过滤，一个 Topic 搞定所有业务，多省事。"

结果半年后，物流想独立扩容做双十一预案，动不了，因为它和订单共用一个 Topic 的队列；监控告警也分不清谁是谁；某天消费积压，三个人对着同一个大盘抓瞎。

这不是省事。这是把三个部门的命运绑在了一条绳上。

今天这篇，我想把这个被用错最多的设计，讲清楚它的底层逻辑。

## 一、本质：Tag 是二级过滤，不是一级分类

很多人把 Tag 当成了"业务分类"，这是最容易被混淆的概念。

RocketMQ 世界里，有两层结构：**Topic 和 Tag 是一级和二级的关系，不是平级的两个分类维度。**

- **Topic，是一级业务边界。** 订单、短信、审计，这是三家不同的业务，各建一个 Topic，各自拥有独立的队列、消费进度、权限和扩容节奏。
- **Tag，是 Topic 内的细类。** 订单 Topic 之下，才有 pay（支付）、refund（退款）这种二级标识。

把 Tag 当分类用，就像一家公司的组织架构：Topic 是事业部，Tag 是事业部下面的产品线。你不会把三个事业部强塞进一个事业部、再用工位号区分彼此——那样事业部本身就失去了意义。

记住一句话：**Topic 划的是"边界"，Tag 划的是"边界里的细分"。这是两个不同量级的决策，不能降维。**

## 二、方法：topic:tag 二级过滤怎么用

清楚了边界，用法就顺了。消费者订阅时，用表达式在 Broker 端做筛选：

```java
consumer.subscribe("TopicOrder", "pay || refund"); // 只收支付与退款
consumer.subscribe("TopicOrder", "*");             // 全收
consumer.subscribe("TopicOrder", "pay");           // 只收支付
```

注意一个关键点：**这个过滤发生在 Broker 端。** 不关心的 Tag，根本不会推送给消费者。省的是带宽，也是算力，更是服务器的心跳。

单元测试也佐证了这一点。我们发了 tagA、tagB、tagC 三条消息，消费者只订阅 `tagA || tagB`，最终断言只收到前两条——tagC 在 Broker 端就被挡在了门外，连一次网络往返都没浪费。

## 三、边界：把分类塞进 Tag，会付出什么代价

我们回到开头的那个反例，把账算清楚。

当你用几十个 Tag 把订单、物流、积分塞进同一个 Topic，你以为省了一个 Topic，其实丢了四样东西：

**第一，独立的扩容能力。** 物流要大促，订单要稳定，它们在同一个 Topic 里共享队列，谁也别想单独扩。

**第二，干净的监控。** 积压告警、消费 TPS 全混在一起，出了问题你分不出是订单慢了，还是物流挂了。

**第三，明确的权限。** 谁能消费订单、谁能消费审计，在 Topic 维度上最容易切分；混在一起，权限只能粗放。

**第四，清晰的 ownership。** 一个 Topic 对应一个团队，责任清晰；混用之后，出了事就是"三个和尚没水吃"。

所以划边界的方法很简单：**当一个东西需要独立扩容、独立监控、独立授权、独立 owner，它就该是 Topic，而不是 Tag。**

## 四、Keys：给消息一张业务身份证

讲完边界，讲两个容易忽略、却极其重要的"配角"。

第一个是 `keys`：

```java
new Message("TopicOrder", "pay", "ORDER-9001", body); // 第三个参数就是 keys
```

`keys` 是你的业务主键，通常是订单号。它不参加过滤，但参加"溯源"。某天用户投诉"我付了钱没收到通知"，你拿订单号去 Dashboard 或 `mqadmin` 按 keys 一查，这条消息从发、到存、到被谁消费，完整轨迹一目了然。

成本几乎为零，出事时却能救命。我的建议很绝对：**每条消息都设 keys。**

## 五、putUserProperty：把"非业务字段"挂上消息

第二个是消息属性透传。有时你想随消息带点额外信息——链路追踪的 `traceId`、用户的 `userId`。

你可以塞进 body，但更干净的做法是 `putUserProperty`：

```java
msg.putUserProperty("traceId", traceId);
msg.putUserProperty("userId", "U-888");
// 消费端
String traceId = msg.getUserProperty("traceId");
```

它适合透传那些"不属于业务体、但排查要用"的字段。body 是给业务的，property 是给工程的——分清楚了，代码才清爽。

## 六、怎么办：Topic 与 Tag 的边界清单

讲到底层逻辑，是为了落地。给你五条清单，照着划：

1. **业务独立就升 Topic。** 需要独立扩容、监控、授权、团队 owner 的，一律建 Topic，别用 Tag 凑合。
2. **Tag 只做 Topic 内细分。** pay/refund、create/cancel 这类，才配叫 Tag。
3. **每条消息都设 keys。** 订单号、交易号，是查问题时的救命稻草。
4. **traceId/userId 走 putUserProperty。** 工程排查字段与业务 body 分离，互不污染。
5. **订阅用表达式精准收敛。** `pay || refund` 比 `*` 更省资源，也更不容易误收。

Topic 划边界、Tag 做细分、Keys 管溯源、Property 做透传。四件套用对，消息队列才真正清爽。
