# 同组消费者，到底是分摊还是广播？

## 一、一个你早晚会踩的坑

先看一个真实得不能再真实的场景。

运营改了商品配置，你希望集群里 3 台机器的本地缓存**全都**刷新一遍——一台没刷到，用户就看到旧价格，客诉就来了。

但同一时刻，一笔订单被支付成功，你希望扣款逻辑**只**被处理一次——如果 3 台机器都扣一遍，用户直接炸毛，财务也对不上账。

同样是"同组消费者"，一个要"每台都干"，一个要"只干一次"。

这两件事，本质不同。RocketMQ 给了你两种模式去对应：**集群模式（CLUSTERING）**和**广播模式（BROADCASTING）**。用反了，要么缓存没刷全，要么钱被扣重。

本质一句话：集群模式是**分摊+横向扩容**，广播模式是**每人一份+本地存进度**。

今天把它掰开揉碎。

---

## 二、集群模式：分摊，是为了"快"

**观点**：集群模式是同组消费者的默认行为。同组起多个实例，Topic 的队列被分摊给它们，一条消息只投递给组内**一个**实例。它的目的不是"公平"，而是**提高吞吐**。

**场景**：你的订单消费来不及了，积压了几万条。怎么办？很简单——在同组里再加一个实例。队列会自动重新分配，新实例分走一部分队列，处理能力近似线性上涨。这就是为什么前面反复强调"队列数 = 并行度"：实例数超过队列数，多出来的实例就是空转的闲人。

**代码佐证**：集群模式什么都不用设，它就是默认值。

```java
// 不调用 setMessageModel，默认就是 CLUSTERING
consumer.subscribe(topic, "*");
```

**解读**：集群模式的核心心智是"**一个活，只该一个人干**"。订单、扣款、发券、写流水，统统该进集群模式。因为业务逻辑上，这些事干重复了就是事故。

---

## 三、广播模式：每人一份，是为了"都干一遍"

**观点**：广播模式下，同组的**每一个**实例都收到全量消息。不是分摊，是复制。一条消息发出去，组里几台机器，就有几分拷贝。

**场景**：回到开头的缓存刷新。假设 3 台应用服务器都各自缓存了一份"商品配置"。配置变更时你发一条消息，希望 3 台本地缓存**同时**失效并重载。这时候必须用广播——每台各刷各的，谁也不替谁。

如果你误用了集群模式，这条消息只会被 3 台里的 1 台收到，另外 2 台的缓存在这一刻就变成了"脏数据"，而且它们自己还不知道。

**代码佐证**：广播和集群的唯一差别，就是这一行：

```java
consumer.setMessageModel(MessageModel.BROADCASTING);
consumer.subscribe(topic, "*");
```

我们在 `BroadcastService` 里就只改了这一行，其余订阅、监听逻辑和集群模式没有任何区别。换句话说，**两种模式在代码上几乎零成本切换，但在语义上是天壤之别。**

**解读**：广播模式的核心心智是"**一个活，每台都得自己干一遍**"。它适合那些"天然分布、彼此独立"的动作——本地缓存刷新、本地配置热更新、各节点的内存状态同步。

---

## 四、最隐蔽的区别：消费进度（offset）存在哪

这是面试常考、生产易踩的点。两种模式，进度存的地方完全不同。

**集群模式：进度存在 Broker 上，按消费组记。**

```text
offset → Broker（"%RETRY%group" 之类）
```

**场景/解读**：某一个实例挂了，它的队列被分给同组别的实例。新实例从 Broker 上的"组进度"继续消费——**无缝衔接**，消息不重不漏。这正是集群模式能"挂了别人顶上"的底气。

**广播模式：进度存在消费者本地。**

```text
offset → 每个实例自己本地维护
```

**场景/解读**：每个实例自己记自己消费到哪。实例重启，从自己本地的进度继续。这意味着广播模式**没法像集群那样"挂了别人顶上接着干"**——因为每台机器的进度是私有的、不可共享的。设计广播消费逻辑时，你必须假设"每台机器各自维护自己的状态"，别指望别人替你记。

> 一句话记住：**集群的进度是"组资产"，广播的进度是"私人物品"。**

---

## 五、第三个坑：广播模式不支持消费重试

很多同学不知道这一点，踩了才后悔。

**观点**：广播模式下，消息消费失败**不会**被重投，也没有重试队列。

**场景**：你用广播做本地缓存刷新，结果某台机器当时连接数据库超时，刷新失败了。在集群模式下，这条消息会进重试队列，过会儿再来一遍，总能成功。但在广播模式下，这次失败就**永久丢失**了——Broker 不替你保存重试进度，因为每个实例进度都在自己本地，Broker 根本无从判断"该不该再投一次"。

**解读（方法）**：所以广播消费者的监听器，**几乎总是无脑返回 `CONSUME_SUCCESS`**（我们的 `BroadcastService` 就是这么写的）。因为即便返回失败，也不会触发重试，反而容易误导读代码的人。正确的做法是：广播逻辑要足够健壮，自身做好幂等与容错，而不是依赖 MQ 的重投。

---

## 六、怎么办：给你一张落地清单

讲了这么多，落到选型上，记住下面四条就够了：

1. **订单、扣款、发券、写流水**——一律集群模式（默认）。要的是"分摊、只干一次、不能重复"。
2. **本地缓存刷新、配置热更新、节点内存状态同步**——用广播模式（`setMessageModel(BROADCASTING)`）。要的是"每台都干一遍、彼此独立"。
3. **广播消费者别依赖重试**：逻辑自己兜底，监听器直接返回成功，别把可靠性寄托在 MQ 重投上。
4. **进度存储心里有数**：集群进度在 Broker（可故障转移），广播进度在本地（私有、不可共享）。扩缩容、重启、排障时，这个差异决定了你能不能"接着干"。

把"该分摊的"设成广播，后果是重复扣款；把"该广播的"设成集群，后果是部分节点没刷新。两种都是生产事故，而且都很难第一时间定位。

**本质总结**：集群为"快"——分摊压力、横向扩容；广播为"全"——每台都到、各自为政。选哪个，不取决于你喜不喜欢，而取决于这件事在业务逻辑上，到底"该被干一次"还是"该被每台都干一遍"。
