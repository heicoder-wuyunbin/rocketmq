# 消息发出去了，谁来看？消费者登场

消息发出去了，可没人收，等于白发。

Day2 我们学会了发消息，甚至拿到了回执——消息落在哪个队列、第几个位置，清清楚楚。可如果消息安安静静躺在 Broker 里，没有消费者去取，它就只是一段无人在意的字节，业务不会发生任何改变。真正让消息产生价值的，是另一端——消费者。今天，消费者登场。

动手写代码之前，先点破一个底层逻辑：RocketMQ 的消费者，表面上讲技术，本质上讲"分工"。

---

## 一、"Push"是假象，分工才是本质

你看到的第一个类，叫 `DefaultMQPushConsumer`。名字里有 Push，但请你别被名字骗了。

RocketMQ 的消费者，底层是**客户端长轮询拉**：消费者不停地问 Broker"有我的新消息吗"，Broker 一有就立刻返回，再回调你注册的监听器。所谓"推"，是框架替你不停地"拉"后，又屏蔽了"拉"这个动作，让你产生"消息主动来找我"的错觉。

所以你写消费者时，根本不用自己写 `while(true)` 去轮询。你只注册一个监听器，告诉框架："有消息了叫我。"剩下的拉取、重连、负载均衡，框架全包了。

**观点**：Push 的本质是"我不用管怎么拿，只管拿到后怎么办"。它把"取"的复杂性收编了，只把"处理"留给你。

代码佐证，看注册的这一行：

```java
consumer.registerMessageListener((MessageListenerConcurrently) (msgs, ctx) -> {
    for (MessageExt m : msgs) {
        handler.accept(m);
    }
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
});
```

**解读**：你只写"拿到消息后做什么"（交给 `handler`），以及"做完了告诉你一声"（返回状态）。怎么取、取几条、取不到怎么办，你一行都不用管。脏活留给框架，决策留给你。

---

## 二、消费组：一个被严重误解的"分工单位"

这是 RocketMQ 最容易理解错的概念，也是今天的核心。

消费组（Consumer Group）是 RocketMQ 的**负载均衡单位**。它的运行规则，可以提炼成一句话：**同组分摊，异组各一份。**

**第一，同组多实例 = 横向扩容。**

同一消费组起多个实例，队列被**分摊**给这些实例——一条消息只给组内一个实例处理。这就是集群模式，也是默认模式。

*场景*：订单消费跟不上高峰？不用改代码，同组再加一个实例，队列自动分一份给它，吞吐近似线性提升。这，就是"加机器就能扛"在消息队列里的真实模样。

**第二，不同组 = 多业务订阅。**

不同消费组，每条消息各自消费一份，互不影响。

*场景*：同一个"订单 Topic"，短信组消费一份发短信，审计组消费一份写日志，风控组再消费一份做校验。三个业务各取所需，谁慢谁快都不拖累别人。这才是"一份数据、多处使用"的正确打开方式。

**边界**：这两种行为是正交的——既要靠"同组分摊"扛吞吐，又要靠"异组各一份"让多业务都拿到数据。想混了，架构就乱。

---

## 三、队列数 = 并行度，别让实例"干瞪眼"

顺着"同组分摊"往下想，会碰到一个隐藏的成本陷阱。

一个 Topic 默认只有 4 个队列。如果你同组起了 8 个消费者实例，多出来的 4 个会分不到队列，只能空转，占着资源不干活。

**观点**："消费慢了就加实例"不是无脑加。

*案例*：某团队消费积压，加实例到 8 个，吞吐却纹丝不动——队列只有 4 个，多出的实例全是观众。

**方法**：加实例前先数队列数。实例数超过队列数，加了也白加。要提吞吐，先扩队列（或扩 Topic 并行度），再让实例数对齐队列数。队列数，是你消费能力的天花板；实例数，只是贴着天花板铺的瓷砖。

---

## 四、你返回的那个状态，决定消息的死活

监听器处理完，必须返回一个状态：`ConsumeConcurrentlyStatus.SUCCESS` 或 `RECONSUME_LATER`。

返回 `SUCCESS`，Broker 才认为这条消息消费完了，把消费进度（offset）往前推。返回 `RECONSUME_LATER`，Broker 会把它稍后重试（重试与死信我们 Day11 再展开）。

**这里有个新手必踩的坑：假成功。**

*场景*：你的 `handler` 里调了下游接口，下游抛异常。可你 catch 得不当，异常被吞，方法照常返回 `SUCCESS`。Broker 以为成了、offset 往前推——消息被"假成功"跳过，数据永久丢失，连重试机会都没了。

**观点**：只有真处理成功，才配返回 SUCCESS。异常路径宁可返回 RECONSUME_LATER，也别用 SUCCESS 掩盖失败。状态不是给框架看的礼貌用语，是给消息的一条生路。

---

## 五、Message 不是黑盒，是带标签的包裹

最后，认识一下你拿到的消息本身。`MessageExt` 不是一坨字节，而是结构清晰的包裹：

- `getTopic()`：它从哪个主题来
- `getTags()`：细分标签，订阅时可按表达式过滤（我们代码里写 `"*"`,即全部）
- `getKeys()`：业务主键，排查问题时的"身份证"
- `getBody()`：真正的消息体（字节，需自己转码）
- `getMsgId()`：全局唯一 ID

*佐证*：测试里生产者调用 `producer.send(topic, "order", "k1", "hello-consumer")`，四参数正好对应 topic / tags / keys / body。消费者用 `new String(m.getBody(), UTF_8)` 取出，再用 `CountDownLatch` 确认"收到了、内容还正确"，断言通过。

**解读**：tags 和 keys 看似可有可无，实则是你日后"按业务过滤""按主键溯源"的两根拐杖。今天不埋，明天排查问题时只能对着 body 盲猜。

---

## 六、怎么办：消费者的四条落地清单

把今天内容收敛成一份可执行清单：

1. **认清 Push 是假象**：消费者本质是长轮询拉，你只写监听器、只管"拿到后怎么办"。
2. **用消费组做分工**：同组分摊扛吞吐（横向扩容），异组各一份做多业务订阅；别把两种语义混用。
3. **扩容先看队列数**：实例数别超过队列数，否则空转；要提吞吐先扩队列再对齐实例。
4. **状态如实返回**：真成功才返回 SUCCESS，异常路径用 RECONSUME_LATER，杜绝"假成功"丢数据。

生产者把消息放好，消费者把它取走。中间那个"怎么取、取给谁、取没取成"的学问，是接下来十几天的主题。下一集：Day4，发送还有两种姿势——异步和单向，什么时候该用哪个？
