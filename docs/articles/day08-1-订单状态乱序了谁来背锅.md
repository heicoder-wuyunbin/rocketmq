# 订单状态乱序了，谁来背锅？

你接到用户投诉：刚下的单，App 里先弹了一条"已发货"，三分钟后又弹"已支付"。用户以为自己穿越了——钱还没付，货已经上路了？

这不是玄学，这是消息乱序。今天我们就聊聊 RocketMQ 的顺序消息，看看这口锅，到底该谁背。

## 本质：有序的边界是队列，不是 Topic

先破一个最常见的误解。很多人以为，消息队列嘛，先发的先到、先到先消费，天然有序。错。这个认知，是绝大多数乱序事故的起点。

RocketMQ 保证的从来不是"全局有序"，而是"分区有序"——同一个 MessageQueue 里的消息，严格按写入顺序被消费；而不同队列之间，彼此互不保证。

换句话说，有序的边界是**队列（Queue）**，不是 Topic。你建一个 Topic，背后默认挂着好几个队列。消息一旦分散进不同队列，就各走各的，谁先被消费全看运气。

那"全局有序"能不能做？能。把整个 Topic 缩成一个队列、配一个消费者，全世界自然排好队。代价呢？吞吐直接崩成单线程，生产环境几乎没人这么干。

所以真正落地的解法，是分区有序：我不需要全世界有序，我只需要"同一个订单"的状态有序。于是问题就收敛成一句话——

**怎么把同一个订单的所有消息，钉进同一个队列？**

## 第一、用路由键把业务流锁进固定队列

方法是 `MessageQueueSelector`。生产者发消息时，多传一个"路由键"和一个选择器：

```java
producer.send(msg, selector, orderId);   // arg = 订单号

// selector 的核心逻辑只有一行
int h = arg.hashCode();
return mqs.get(Math.floorMod(h, mqs.size()));  // 按订单号取模选队列
```

关键在哪？`arg` 是订单号。相同的 `orderId`，hash 值永远一样，对队列数取模也永远一样，于是算出来的永远是同一个队列。

订单 ORDER-2001 的"创建 / 支付 / 发货"三条消息，无论何时发出，全进队列 3（举例）。它们在这个队列里天然按发送先后排好队，物理上就不可能被插队。

注意一个常被忽略的细节：取模用的是 `Math.floorMod`，不是 `%`。订单号可能算出负数 hash，`floorMod` 保证结果永远非负，不会因为数组越界而把消息发丢。这才是生产级写法。

## 第二、消费端也要"串行读"，靠队列锁

但只把消息送进去有序，还不够。

消费端如果用我们 Day3 讲的并发监听器，一个队列里的多条消息，会被多个线程同时拉走。你辛苦路由好的顺序，在消费这步又被打乱了。

所以顺序消费必须换 `MessageListenerOrderly`。它对**单个队列加锁**，串行处理这个队列里的消息。锁住期间，其他线程动不了这条队列，顺序就保住了。

返回 `ConsumeOrderlyStatus.SUCCESS` 提交消费进度；如果返回"稍后重试"，它暂停的是**这一个队列**的重试，不影响其他队列正常跑。隔离粒度是队列，设计得很克制。

## 第三、代价：顺序是有价格的

天下没有免费的午餐。顺序消息用两件事换来有序：生产者路由 + 消费者加锁。这两件事的代价，是吞吐。

其一，同订单的消息被迫挤在同一队列，这个订单的流量不可能横向扩展，只能吃单队列的序列化能力。其二，消费端对队列加锁、串行处理，等于主动放弃了并发消费的速度红利。

所以顺序消息的正确用法是：只给真正需要顺序的业务上锁。订单状态、账户流水、库存扣减这类"顺序错一笔就资损"的场景，值得；而日志、通知、埋点这类"顺序无所谓"的消息，千万别用，白白牺牲吞吐。

## 实战：订单状态机不再穿越

代码里 `sendOrderEvent(topic, orderId, status)` 就是这样用的。订单 `CREATED → PAID → SHIPPED`，全部按 `orderId` 路由，三事件进同一队列、顺序消费。下游的风控、审计、物流状态机，看到的永远是"先创建、再支付、后发货"。

Day08 的单元测试 `Day08SequenceTest` 也验证了这点：对 ORDER-2001 连发 CREATED / PAID / SHIPPED，断言消费到的顺序严格是三者依次——测试绿了，锅就甩出去了。

## 怎么办：落地四清单

1. **先问"要不要顺序"**：只有存在"错序即错误"的业务（订单、账务、库存），才上顺序消息；其余一律普通并发消费。
2. **路由键选对**：用业务主键（订单号 / 用户号）做路由键，保证同业务流进同队列；忌用随机值或时间戳。
3. **消费端配对**：用了顺序发送，就必须用 `MessageListenerOrderly`，否则前功尽弃；重试用 SUSPEND 而非抛异常。
4. **取模用 `floorMod`**：路由计算务必非负取模，防 hash 负数导致越界丢消息。
5. **容量心里有数**：同 key 流量受单队列单线程约束，热点订单可能成瓶颈，必要时按 key 分桶再取模。

顺序消息不神秘，本质就一句话：**用路由键把同一业务流锁进同一个队列，再对队列加锁串行消费。** 少一步，就乱序；两步都做对，锅就不在你这。
