## 00:00 开场钩子（0:00 - 1:30）

【画面】标题卡 → 讲师小窗

> 很多人写 RocketMQ / 发了就完事 / 从不看返回值。/ 直到消息"好像丢了" / 查日志才发现 send 早报超时 / 代码里没处理。/
>
> 今天 / 我们把 send 返回的 SendResult / 拆开看。

## 01:30 生命周期（1:30 - 4:00）

【画面】四步流程图：new→setNamesrv→start→send→shutdown

> Producer 四步 / new 出来 / 设 namesrv 地址 / start / send / 最后 shutdown 释放。/
> start 前发会报错 / 不 shutdown 泄漏连接。/ 四步缺一不可。

## 04:00 SendResult（4:00 - 7:30）

【画面】SendResult 字段卡片：msgId / sendStatus / messageQueue / queueOffset

> send 是同步 / 阻塞等 Broker 回执。/ 回执四样：/
> msgId 查消息用 / queueOffset 队列里第几位 / messageQueue 哪个队列。/ 两者加起来 / 唯一锁定消息在磁盘的坐标。/ 消费进度就是"队列消费到第几个" / 记住这个。

【留存锚点】"queueOffset 为什么重要 / 它是消费进度的依据 / 评论区扣 2。"

## 07:30 四种状态（7:30 - 10:30）

【画面】四状态表：SEND_OK / 三个异常

> 默认你只看到 SEND_OK。/ 但还有三个：/ 刷盘超时、同步从超时、从不可用。/
> 意思是消息可能只在内存 / 没落盘 / Broker 一宕机就没了。/ 生产环境看到这三个 / 必须告警。

## 10:30 重试不等于去重（10:30 - 13:00）

【画面】重试图：网络断了又发一次 → Broker 两条重复

> setRetryTimesWhenSendFailed(3) / 发送失败重试 3 次。/ 但坑在这：/ 重试可能产生重复消息。/ 所以重试解决"网络别丢" / 不解决"业务别重复" / 后者消费端管 / Day11 讲。
