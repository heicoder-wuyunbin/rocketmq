# 主挂了，谁来顶上：RocketMQ 高可用的底层逻辑

凌晨三点，你被电话叫醒：交易链路大面积超时，下单全失败。你冲到电脑前，监控一片红——Broker 主节点宕机了。从节点有数据，但没人把它提升成新主。你手忙脚乱改配置、重启、切流量，两小时过去，交易才恢复。

这一夜的代价，本来可以避免。

今天我们就把"主挂了谁来顶上"这件事，从底层逻辑讲到落地选型。

## 一、本质：高可用不是堆机器，是消灭单点

很多团队一说高可用，第一反应是"多加几台"。这是误区。

高可用的本质只有一句话：**消灭单点，并在单点消失后自动接替**。

RocketMQ 里有两个角色，对"单点"的态度完全不同。一个故意做成了无单点，另一个才是真正的单点战场。先看前者。

## 二、第一层：NameServer 为什么"佛系"反而稳

NameServer 是路由中心，相当于"通讯录"：告诉生产者、消费者"消息该发给哪个 Broker"。

它的设计很反直觉：**NameServer 之间互不通信**。

每个 NameServer 各自维护一份路由表，Broker 定期来报心跳。你部署 3 个 NameServer，它们之间不聊天、不复制、不选举。挂掉一个，其余照常工作；客户端还缓存着路由，已经建连的收发完全不受影响。

为什么不搞成 ZooKeeper 那样的主从同步？因为 RocketMQ 故意把 NameServer 做成**无状态、可水平扩展**的弱依赖。它本身就不是单点瓶颈——你多部署几个就完了，没有"主"需要切换。

> **观点**：NameServer 用"无状态 + 互不通信"消灭了自身这个单点。真正的单点风险，在 Broker。

## 三、第二层：Broker 主从，是"一致性"和"性能"的拔河

Broker 是真正存消息的"邮局仓库"。单个 Broker 挂了，这个分片的读写全停。所以它必须主从。

但这里有两个容易被混为一谈的维度，必须分开看。

**维度一：复制（主从之间）**
- **同步双写（SYNC_MASTER）**：主写完，必须等从也写完成才给客户端返回。主挂了，从有全量，不丢。代价是写入多一跳网络，慢。
- **异步复制（ASYNC_MASTER）**：主写自己磁盘就返回，后台异步同步给从。快，但如果主突然断电，那一点点还没同步过去的数据就没了。

**维度二：刷盘（Broker 内部）**
- **SYNC_FLUSH**：消息真正落盘才返回。机器掉电也不丢，但每次写都要等磁盘 IO，慢。
- **ASYNC_FLUSH**：写进操作系统的 page cache 就返回。快，可一旦宕机，cache 里没落盘的消息就丢了。

这两个维度**正交组合**。最稳的是"同步双写 + SYNC_FLUSH"，最怕丢数据的金融场景选它；最快的是"异步复制 + ASYNC_FLUSH"，吞吐优先、能容忍少量丢失的日志场景选它。

> **观点**：复制管"主从之间丢不丢"，刷盘管"Broker 自己掉电丢不丢"。先把这两个边界分清，才不会一出事就瞎猜。

## 四、第三层：传统主从的死穴——主挂要人工切

同步双写的主从，数据上是安全的：主挂了，从有全量。但有一个尴尬的现实：**得有人把某个从提升成新主**。

切换期间，这个 Broker 组的写入是停摆的。对小业务，停几分钟能忍。对中大业务，停两小时就是事故——就像文章开头那一夜。

所以，传统主从解决的是"数据不丢"，没解决"服务不中断"。

## 五、第四层：DLedger，让主从自己选老大

DLedger 用 Raft 协议，把一组 Broker（比如 3 副本）组织起来：一个 Leader（主），多个 Follower（从）。

主挂了，Raft 会在存活副本里**自动选举**出新 Leader，秒级切换，不停服。你不用半夜爬起来切主，系统自己把位子补上了。

这才是生产级的高可用：复制、刷盘、自动切换，三件事一起闭环。

代码中我们用一个建模类把这套逻辑固化。`HaDeployService` 里有两个工厂方法值得看：

```java
public static HaDeployService dledgerCluster(int brokerGroups) {
    return new HaDeployService(3, brokerGroups, 2, FlushPolicy.SYNC, ReplicaMode.DLEDGER);
}
public static HaDeployService masterSlave(int brokerGroups) {
    return new HaDeployService(2, brokerGroups, 1, FlushPolicy.ASYNC, ReplicaMode.MASTER_SLAVE);
}
```

`dledgerCluster` 默认就是 3 个 NameServer、每组 1 主 2 从、同步刷盘、DLedger 模式；`masterSlave` 则是 2 个 NameServer、1 主 1 从、异步刷盘。测试里 `dledgerCluster(3)` 断言出 9 个 Broker（3 组 × 1 主 2 从），拓扑正确即可进入部署评审。

> **观点**：DLedger 的价值不是"多了一个副本"，而是把"人工切主"这个最贵、最慢、最容易出错的环节，自动化掉了。

## 六、部署拓扑与选型：按规模给答案

讲完底层，直接给框架化的选型建议：

| 规模 | 推荐拓扑 | 取舍 |
|:---|:---|:---|
| 小团队 / 测试 | 单 Broker + 2~3 NameServer | 省机器，接受丢风险 |
| 中型生产 | 主从同步双写 + SYNC_FLUSH + 3 NameServer | 不丢，主挂需人工切 |
| 大型 / 不能停 | DLedger 3 副本 + 3 NameServer | 自动切换，近零中断 |

## 七、怎么办：生产环境的 5 条落地清单

1. **NameServer 永远部署 3 个**，无状态互不通信，别省这一步。
2. **先分清两个维度**：复制管主从丢不丢，刷盘管掉电丢不丢，选型时分别确认。
3. **金融/交易类选"同步双写 + SYNC_FLUSH"**，用延迟换不丢；日志/埋点类可放宽到异步。
4. **中大型生产直接上 DLedger 3 副本**，别把"主挂人工切"留成定时炸弹。
5. **上线前跑通切换演练**：主动 kill 主节点，验证秒级自动切换和消息零丢失，而不是等事故夜来验证。

高可用从来不是"加机器"那么简单，它是"复制策略 + 刷盘策略 + 自动切换"三道题的组合解。想清楚每一项的边界和取舍，你的系统才配得上"生产环境"四个字。
